# Generated SNOMED settings on the existing dev worker

The `snomed-properties-v1` profile connects the bounded [offline configuration generator](snomed-configuration-generation.md) to preparation and native execution. It retains the exact September 2026 source engine, March replacement baseline, native inputs, historical ID bounds, metadata/ICD inventories and official output references. It changes how `etc/sct.cfg` is supplied; it changes no RF2 transformation or representation policy.

The original `as-produced` case and `snomed-properties-preview-v1` behavior remain available. A separate reviewed `generated-configuration` case is required to execute generated settings. The preview profile cannot be relabeled as execution merely by changing its profile field or supplying it directly to preparation.

## Frozen generation and worker transport

`snomed_configuration.execution_recipe_from_lock(lock)` verifies the completed common checksum, exact source/case/configuration bindings, the three-field generation specification, captured cfg identity, native/metadata dependencies and any already-frozen recipe. It recomputes the complete recipe rather than accepting hashes of arbitrary settings. The resolver alone can use `verify_checksum=False` before attaching its final checksum; this retains the remaining source/specification/artifact checks. The common worker validates the complete lock before preparation or execution.

The shared worker package carries two new fields for this case:

```text
generated_configuration = lock.configuration_generation
configuration_generation_inputs = {
    configuration: lock.configuration,
    artifacts: lock.case.artifacts
}
```

The recipe contains the pinned cfg template payload and generated file payload. Preparation and the native runner call `validate_execution_recipe(...)` to recompute that recipe from its common inputs, verify the selected conversion contract and bind the captured cfg payload in `code_files`. The template path/hash is fixed to the reviewed capture; the source engine remains `3b125edc1d29f7c7a91673da2a8d752bb0adff44`.

`prepare_snomed_candidate.prepare(...)` accepts the new fields as optional keyword arguments. It verifies them before candidate staging, extracts only the eighteen declared input files, and stages the four remaining source code/documentation files. It retains the captured `etc/sct.cfg` descriptor under `configuration_templates`, without copying that cfg into place. The generated recipe alone writes `etc/sct.cfg`, with mode `0444`. The preparation receipt records `configuration_seeded_from_code_files: false` and compact generated/template identities. With no generated fields, the original five-file staging and original modes are unchanged.

`verify_generated(recipe, target)` checks generated bytes, hashes, exact read-only mode and file/directory symlink substitution. `run_snomed_core_replay.verify_case(...)` also recomputes the transported recipe and verifies the actual cfg. The runner repeats generated-cfg verification after conversion, after the existing dangling-attribute cleanup, and during final case revalidation. Native core/result records carry a compact generation receipt; payload bytes are not duplicated in those receipts.

## Local verification and retained execution gate

`python3 -B tools/check_snomed_generated_execution.py` exercises a real tiny archive through the production preparation function. It verifies eighteen-file selection, exclusion of archived completed core output, generated cfg writing/mode, separate template provenance, input/code verification, writable/changed/symlinked cfg rejection, tampered recipes/contexts and original five-file staging. Only host/capacity and the platform-specific Linux publication boundary are mocked. It does not run an RF2 conversion or change any server runtime.

The existing 56 configuration-preview checks and 25 replay/comparison/runtime-preservation fixtures also pass. The [execution fixture record](snomed-generated-execution-fixtures-20261110.json) binds the actual tool hashes and test counts. Source-module tests do not replace the common resolver/worker integration checks or the required fresh native dev replay.

The generated cfg remains byte-exact to its captured historical template, SHA-256 `56b214ee51d698f716a1701ca387543ac161baf8f1618c9a5f51f044147465b3`. A native execution must still complete conversion and cleanup, compare all five outputs against the frozen official references, pass independent structural validation and reverify inputs/code/runtime/generated settings/outputs. Inversion attributes retain the pre-enrichment `attributes.orig` reference. The existing global runtime lock serializes full inversions on the same dev worker; no additional worker environment is introduced.

This profile establishes historical generated-settings execution only. New-release acquisition, arbitrary RF2 package conventions, metadata generation/installed state, production ID allocation, live legacy QA, insertion and production approval remain separate gates. A recipe's historical execution flag is not production eligibility.
