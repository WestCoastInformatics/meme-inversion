`append_atn.pl:13,36–45` embeds the current SAB, reads `orig/mdr_by_version.txt`, and appends attributes for current PT/LLT/OL codes. `README.INVERSION:136–144` says the history producer runs on NLM infrastructure and its output is transferred to NCI. Treat the preserved history file as an input with provenance. Replacing its producer is separate work.

RADLEX's runbook names a generic BioPortal CSV, but the actual `concat.pl:7` reads `RADLEX_no_german.csv`. The capture includes that file and a separate removed-German-synonym file; it does not establish the process that produced them. A prepared-input replay can proceed once those identities and the downstream boundary are frozen. A publisher-to-output replay additionally needs that preparation decision and producer. `make_vb.pl:7–28` introduces a specific `Text::CSV` dependency and pipe-escaping policy to characterize.

The RADLEX wrapper cleanup is part of the production result, not generic comparison normalization (`bin/invert_RADLEX.s:5–18`). Its atom cleanup retains the first `(termgroup, code, string)` record and removes merges referencing dropped SAIDs; attribute cleanup keys on `(id, ATN, ATV)`; relationship cleanup keys on endpoints/REL/RELA with special SRC handling. Preserve these exact rules for the first replay. Subsequent review must check whether discarded scope, qualifier or other fields can differ, and whether atom cleanup leaves any other references to removed SAIDs. Do not silently reproduce these keys in a comparator that hides differences.

## Prior data, insertion and the common request

Both folders contain `src/attributes.orig` and a larger `src/attributes.src`. Both runbooks explicitly move default semantic-type generation into insertion (MDR README lines 188–192; RADLEX README lines 101–107). Archive/content verification on November 6 now confirms the stage distinction described below. Bind each reference member explicitly; do not assume that every `attributes.orig` has the same provenance or filter all semantic types.

Source/termgroup metadata preparation can query the database through `dump_src_info.pl`. Its saved results are sufficient conversion inputs when verified. A database used for later QA or insertion has a different role. Prior release folders used for change comparison, historical identity state, and inherited code must remain distinct; the code-copy relationship creates no automatic data dependency.

Both cases also consume saved hierarchy-root identities: `HC.RootNodeSaid` is `124407941` for MDR and `116482203` for RADLEX. MDR inherits `MakeRoot = 0` from shared defaults; RADLEX sets it explicitly. MDR's `readHierInfo` and RADLEX's `getParChd` install these configured roots in the hierarchy. These are preserved identity inputs even though conversion need not query a database or read a prior folder to obtain them. Their cases must trace the actual emitted root references and define verification of persistent external anchors. A validator that requires every referenced root SAID to appear among newly generated atoms cannot be reused without that source-specific review. This does not require reconstructing the whole historical database.

The [registry](source-registry.json) recognizes `MDR` and `RADLEX`. Requests use the same `source`, `version`, `engine_ref`, `case_variant`, `reference_stage` and `comparison_profile` fields as other sources. The resolved configuration uses the same `inputs.source_data`, `inputs.source_data_stage`, baseline and provenance vocabulary. Typed source options should be added only after their actual consumers are traced. No fallback to the NCIt, SNOMED or MTH engine is permitted.

For MDR, a preserved historical code/version bundle can be named through `publisher_history`; it does not require staging every older MDR release folder. The abbreviation/translation tables should be captured as versioned representation inputs under `policy_ref`, rather than copied untracked from a prior release. RADLEX's CSV preparation/escaping and cleanup rules likewise belong to versioned code/policy. A prepared-input case must identify which of those stages already produced its starting bundle. These are mappings into the common vocabulary, not additional aliases for common parameters.

For each source, the next characterization case should freeze the matching S3 archive, verify the imported production code, preserved input closure and actual runtime, establish the pre-insertion output map, then execute an unchanged-engine replay and source-specific validation on dev. These are additional coverage cases; their infrequent schedules do not require a different request interface or block implementing the three initially characterized sources.
