## Current source versions and source families

The captured `INV/bin/api_metadata.sh` calls `/metadata/terminology/current`. Its matching REST implementation creates a metadata service for that request, calls `getCurrentTerminologies`, resolves its response and closes the service. The JPA method selects `TerminologyJpa` records with `current = 1`. This establishes the meaning of that endpoint in the reviewed revision; it supplies current terminology/version objects, without asserting an October state. ## Identifier meanings cannot be interchanged

The atom loader explicitly documents and implements this mapping from `classes_atoms.src`:

| Identity | Reviewed Java representation | Meaning for capture |
|---|---|---|
| Backend atom identity | `AtomJpa.id`, inherited from generated `AbstractComponent.id` | Used by `/content/atom/{atomId}`; it is not the inverter's SAID. |
| Source atom ID, field 0 | `Atom.alternateTerminologyIds[projectTerminology + "-SRC"]` | This is the identity needed for existing SAID consumers. The project terminology must be established, rather than assumed from the source abbreviation. |
| Source atom unique identifier, field 9 | `Atom.terminologyId` | SAUI; distinct from both generated backend identity and SAID. |
| Source concept identifier, field 10 | `Atom.conceptId` | SCUI; not the containing NCImeta concept's backend ID. |
| Source descriptor identifier, field 11 | `Atom.descriptorId` | SDUI; not SAID. |
| Project atom identity | Another alternate-terminology entry keyed by the project terminology | The loader records its computed AUI separately from the `-SRC` entry. |

[Atom loader, lines 165–225 and 269–274](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/algo/insert/AtomLoaderAlgorithm.java#L165-L225), [generated component identity, lines 38–70](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-model/src/main/java/com/wci/umls/server/jpa/content/AbstractComponent.java#L38-L70).

## SRC/RPT retrieval is affected by response handlers

The reviewed release writer locates root concepts by source code `V-<terminology>`, atom terminology `SRC`, and atom term type `RPT`. These are code-supported root filters, rather than a guessed database schema. [WriteRrfMetadataFilesAlgorithm, lines 253–257](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/algo/release/WriteRrfMetadataFilesAlgorithm.java#L253-L257).

However, finding an atom is insufficient if the serialized response omits its SAID. `/content/atom/{atomId}` chooses graph resolution using the atom's terminology. `DefaultGraphResolutionHandler.resolve(Atom)` explicitly clears `alternateTerminologyIds`; its code resolver calls the same atom resolver. A direct SRC atom/code response can therefore discard the required identity. [Atom endpoint, lines 1250–1276](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/rest/src/main/java/com/wci/umls/server/rest/impl/ContentServiceRestImpl.java#L1250-L1276), [default handler, lines 149–158 and 271–285](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/services/handlers/DefaultGraphResolutionHandler.java#L149-L158).

The full-concept query endpoint `/content/concept/{terminology}/{version}/get` instead resolves using the requested concept terminology. `UmlsGraphResolutionHandler` resolves each concept atom and retains alternate IDs. Indexed `prod-nci-meta` configuration selects that handler for `NCIMTH`, and the default handler for other terminologies. This provides a plausible existing read route through full NCImeta concepts, contingent on the deployed configuration. It has not been exercised here. [Full-concept endpoint, lines 1395–1435](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/rest/src/main/java/com/wci/umls/server/rest/impl/ContentServiceRestImpl.java#L1395-L1435), [UMLS handler, lines 22–78](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/services/handlers/UmlsGraphResolutionHandler.java#L22-L78), [indexed handler configuration](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/config/prod-nci-meta/src/main/resources/config.properties).

A future capture must validate all three root filters on the returned individual atom, retain its project `-SRC` identifier, reject ambiguity/missing IDs, and prove pagination/index completeness. A search returning the first matching concept is not a complete installed-root export. No exact `findRootHierarchy`, `findRoot`, `getRootHierarchy` or `getSrcAtomId` producer was found in the reviewed inversion tree or scoped indexed-backend searches; these negative searches do not prove that deployed/custom code lacks such a producer.

## Termgroup ranking state differs from generic term types

The metadata loader resolves each versioned source string to its root terminology, constructs high/low **root-terminology/TTY pairs**, and validates low pairs against the default precedence list or other incoming high pairs. It subsequently updates both default and project precedence lists. [MetadataLoaderAlgorithm, lines 158–209, 239–285 and 953–1038](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/algo/insert/MetadataLoaderAlgorithm.java#L158-L209).

`/metadata/precedence/{terminology}/{version}` selects the stored precedence list for that exact project terminology/version; a separate ID endpoint also exists. Its pairs are not a literal installed `VSAB/TTY` table. Generic `/metadata/termType/{terminology}/{version}` selects term-type definitions and cannot establish a particular source/type's ranking membership. [Precedence endpoint, lines 300–335](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/rest/src/main/java/com/wci/umls/server/rest/impl/MetadataServiceRestImpl.java#L300-L335), [JPA lookups, lines 221–239 and 579–592](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/services/MetadataServiceJpa.java#L221-L239), [precedence pair interpretation, lines 344–355](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-model/src/main/java/com/wci/umls/server/jpa/helpers/PrecedenceListJpa.java#L344-L355).

Archived `MRRANK.RRF` is also insufficient to claim complete ranking state: the release writer filters out precedence pairs without publishable atoms. A defined ranking anchor can therefore be absent from that release file. Capturing rank definitions, generic TTY metadata and observed source atoms answers different questions. [MRRANK writer, lines 95–132](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/algo/release/WriteRrfMetadataFilesAlgorithm.java#L95-L132).

The loader stages source terminology metadata before term types and precedence, committing between stages. Within term-type loading, it retains the first `termgroups.src` row for each TTY abbreviation; changes to existing term-type suppression/exclusion flags are explicitly disabled in favor of UI maintenance. Precedence insertion can make repeated passes when a new high pair depends on another new pair, and fails if unresolved pairs make no progress. File ordering alone cannot approve a missing rank target or change an existing global TTY flag. [Term-type handling, lines 846–938](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/algo/insert/MetadataLoaderAlgorithm.java#L846-L938), [precedence dependency passes, lines 974–1027](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/algo/insert/MetadataLoaderAlgorithm.java#L974-L1027).

This is a material boundary for the existing offline `ncimeta-installed-state-v1` preflight: literal versioned termgroup inventory is a declared preview model, not demonstrated equivalence to deployed JPA precedence semantics. No schema/preflight change was made during discovery. The operational capture contract needs review against the deployed loader before using such a snapshot for readiness. This evidence does not decide whether CELLOSAURUS/SY was present in the relevant database state or whether the historical ranking should change.

## No coherent capture boundary has been established

The reviewed REST endpoints create and close separate service objects per request and expose no shared frozen-state token in the inspected method signatures. The metadata loader commits between terminology and term-type/precedence stages, so a sequence of current-service calls could observe different stages of an insertion. [REST getter lifecycle](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/rest/src/main/java/com/wci/umls/server/rest/impl/MetadataServiceRestImpl.java#L263-L294), [loader transaction stages, lines 296–319](https://github.com/WestCoastInformatics/UMLS-Terminology-Server/blob/708f088babd3e5d16016ab9016af9fee01f2921b/jpa-services/src/main/java/com/wci/umls/server/jpa/algo/insert/MetadataLoaderAlgorithm.java#L296-L319).

No atomic multi-export mechanism was established by this scoped review. This is a limitation of the reviewed evidence, not a claim that every possible repository/deployment mechanism was exhaustively ruled out. A subsequent step should identify the deployed build and nonsecret handler selections, verify a real response/export with preserved SAIDs and complete default/project ranking state, and establish a supported coherent state boundary. Current responses must not be relabeled as reconstructed historical state. No new SQL or speculative exporter is proposed.

The next capture contract therefore needs an explicit project terminology/version and its `-SRC` alternate-ID key; individually verified SRC/RPT `V-<RSAB>` atom selection and unambiguous SAIDs; root-terminology family plus current/exact version metadata; separately identified default and project RSAB/TTY precedence lists; reviewed active replacement membership; and one supported consistent state boundary. The full-concept route is a code-supported candidate to investigate, not a validated complete export. Capture must retain raw evidence and deployed producer/handler identity before any assembler or operational preflight revision is accepted.

The later [deployment inspection candidates](nci-deployment-inspection-candidates.md) narrow the build/configuration/project evidence to collect, and the [v2 raw-bound preflight](nci-backend-preflight-v2.md) implements a separate offline review contract. Neither establishes a real deployed capture or clears operational eligibility.
